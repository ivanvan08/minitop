# Бізнес-логіка рішень minitop

Це політика, а не опис коду: кого minitop оцінює, коли повторює оцінку, що віддає
моделі і як бал стає кольором. Будова модулів - у [engineering-decisions.md](engineering-decisions.md), вартість - у
[project-overview.md](project-overview.md) та [model-evaluation.md](model-evaluation.md).

## 1. Кого оцінюють

Оцінюється кожен процес, крім тих, чию безпечність доведено походженням файлу
або процесу. Рішення ухвалює `trust_is_trusted()`, а
`model_engine_tick()` пропускає рядки з `trusted`.

| Правило | Умова | Звідки береться |
|---|---|---|
| C | exe належить пакету з репозиторію `core` або `extra` | `pacman -Qo` пакетно, множина з `pacman -Sl core extra` |
| E | exe-лінк не читається і `ppid == 2` | `/proc/<pid>/exe` плюс `/proc/<pid>/stat` |
| H | `ppid == 1` і шлях починається з `/usr/` | `/proc/<pid>/stat` і шлях процесу |

- **C.** Пакет зараховується, лише якщо він є в `core`/`extra`; AUR і локальні
  збірки не довірені. Чому: ці репозиторії підписує дистрибутив, а AUR - код користувача.
- **E.** Порожній exe-лінк **і** `ppid == 2`; сама назва в дужках не доказ, бо її
  ставить `prctl`, і у VM зразок під `/dev/shm` назвався `kswapd0`. Чому: тільки
  дитина `kthreadd` гарантовано не виконує користувацький код.
- **H.** `ppid == 1` плюс системний шлях. Чому: systemd запускає лише описане в
  його юнітах і тримає бінарники поза домашніми теками.

**Гейт `argv`/uid.** Не-root minitop не читає `/proc/<pid>/exe` чужого
користувача, тому `procs_collect()` бере перший аргумент з `cmdline` і ставить
`exe_from_argv`. Для такого шляху C і H зараховуються тільки при `uid < 1000`,
E - завжди. Чому: `argv[0]` контролює сам процес, і `PR_SET_DUMPABLE=0` досить,
щоб сховати лінк і назватися `/usr/bin/sshd`; системний uid не підробити.

Довіра - економія викликів, а не твердження «безпечно». Рядок
показує `ok` приглушеним зеленим; якщо стоїть DEL, TMP або MEMFD, позначку не
малюють, бо робочий образ уже не той файл, який поставив пакет.

## 2. Коли оцінюють повторно

- **Новий процес** отримує запис розкладу з `next_allowed = 0`, тому перший же
  прохід після появи ставить його в чергу; ключ - pid плюс `starttime`.
- **Повтор** бере `model.resample_sec` (1500 с) і множить на випадкове 0.8..1.2,
  тобто 20-30 хв, з новим інтервалом після кожної відповіді. Чому: фіксований
  розклад - це розклад, під який імплант може підлаштуватися.
- **Черга** обмежена: до 300 нових запитів за прохід у порядку pid, не більше
  чотирьох одночасно; LLM - до 10 за прохід. Запит у польоті не дублюється.
- **Очікування** не маскується під вердикт: до першої відповіді моделі в FLAGS
  прочерк, а в режимі 3 рядок вище порогу показує бал приглушеним, поки LLM не
  відповість.

## 3. Що бачить модель

Запит збирає `model_build_request()`; кожне поле відповідає на своє питання.

| Поле | Навіщо воно там |
|---|---|
| `comm` | назва, яку процес обрав сам; цінна лише для порівняння з `exe_path`, не як доказ |
| `exe_path` | лінк ядра: ` (deleted)` означає видалений файл, порожнє значення - нечитабельний лінк |
| `cwd` | робоча тека: staging у `/tmp` чи `/dev/shm` є окремим класом ознак |
| `user` | клас привілеїв; сам root не є підозрою, підозра - root плюс user-writable шлях |
| `cpu_pct_irix` | 100 означає одне завантажене ядро, тому 400 - чотири; форма майнера чи брутфорсу |
| `rss_mib` | вага процесу: безфайловий payload часто тримає помітний обсяг у пам'яті |
| `local_flags` | DEL, TMP, MEMFD пораховані локально, щоб модель не виводила їх з рядка повторно |
| `listening_ports` | лише TCP LISTEN; порожній список не є доказом невинності, бо процес може тільки виходити назовні |
| `package` | name, version, desc, repo; об'єкт відсутній цілком, коли пакет невідомий |

`NET` окремим прапорцем не дублюється: його подає список портів. Метадані пакета
читаються з локальної бази pacman, опис обрізається до 120 байтів на межі UTF-8,
а `%NAME%` звіряється, щоб `bash` не отримав опис `bash-completion`.

`repo` заповнюється `core`/`extra` лише для довіреного пакета; для AUR він
порожній. Чому: модель має відрізняти «пакет є» від «пакет із підписаного джерела».

## 4. Від бала до кольору

Рівнів десять, один бал - один рівень; критерії лежать у `RISK_CRITERIA`, а
відповідь API `score` (нуль-базований індекс) стає `round(score) + 1`. Поріг 5
- це перший рівень, чиї критерії описують конкретну ознаку ухилення, тому
звичайна й трохи незвична робота лишається синьою.

- **Режим 1:** лише локальні прапорці DEL/TMP/MEMFD/NET, без мережі й вердикту.
- **Режим 2:** цифра рівня; 5 і вище - червона клітинка, нижче - синя, довірені
  показують `ok`.
- **Режим 3:** цифра рівня плюс вердикт LLM; нижче порогу синя остаточно, вище -
  приглушена до відповіді, далі синя або червона.

У режимі 3 смуга для LLM виводиться з порогу: `min_level = threshold`,
`max_level = 10`. Червону клітинку там ставить тільки вердикт LLM з поясненням
(`llm_verdict == 1` і непорожній `llm_reason`). Чому: бал моделі тут - фільтр і
оцінка підозри, а червона клітинка - заява про шкідливість із reasoned verdict.

## 5. Політика відмов

- **Немає ключа, файл не читається, libcurl не ініціалізувався:** рушій не
  створюється, сірий режим фарбує кожну клітинку тьмяним прочерком.
- **Мережа, HTTP або 2xx без придатного бала:** рівень лишається `-1`, у звіт
  невдала спроба не йде, 2xx без бала пише `level: -1`; клітинка - тьмяний прочерк.
- **Обрізана відповідь LLM:** якщо рядок `VERDICT` уже прийшов, вердикт
  зараховується, а reason отримує ` [truncated]`; інакше бал `-1`, клітинка сіра.
- **Таймаут або 5xx LLM:** попередній кешований вердикт лишається, у звіт
  нічого не додається, повтор - після `llm.resample_sec` (1800 с).
- **Немає pacman або він не відповів:** усі нерозпізнані шляхи стають
  недовіреними й оцінюються; це дорожче, але безпечний напрямок відмови.
- **Нічого не оцінюється двічі:** невдала спроба теж зсуває `next_allowed`, тому
  мертвий endpoint не крутить той самий процес щокадру.

## 6. Чого інструмент не робить

- **Не читає `/proc/<pid>/environ`**: там ключі й токени, і жодне
  правило minitop їх не потребує.
- **Не надсилає `cmdline`.** Він читається лише як резервне джерело `argv[0]`,
  коли exe-лінк недоступний, і не потрапляє ні в запит, ні в звіт; це в тестах.
- **Не вбиває без підтвердження:** `x` питає `SIGTERM <pid> <comm>? y / n` і шле
  сигнал лише після `y`; повторний `x` після SIGTERM пропонує SIGKILL;
  `navigation = false` робить `x` інертним.
- **Не оцінює той самий процес у вікні** і не оцінює довірені взагалі: ні
  модель, ні LLM не отримують рядок, для якого `trusted` або час ще не настав.
- **Не пише ключ нікуди**, крім заголовка `Authorization`: ні в argv, ні в
  stderr, ні у звіт.
- **Не обіцяє безпеки.** Довіра, синя клітинка й прочерк - різні твердження:
  перша про походження файлу, друга про оцінку, третя про відсутність оцінки.
